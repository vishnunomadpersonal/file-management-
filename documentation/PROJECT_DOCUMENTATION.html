1. Executive Summary

This is a production-grade enterprise document management platform that combines traditional file storage with cutting-edge Incremental Machine Learning (ML) pipelines. The system is inspired by Incremental View Maintenance (IVM) concepts from database research, applying them to ML model updates.

🎯 Key Innovation

Instead of retraining ML models from scratch on every data change, we apply database-inspired techniques to update models incrementally - saving up to 95% of computational resources.

Key Features

  • Chunked File Upload - Large files split into 5MB chunks for reliable uploads
  • Multi-Tenant Architecture - Organization-based file isolation
  • Virus Scanning - ClamAV integration for malware detection
  • Event-Driven Processing - RabbitMQ with DLQ, retries, priority queues
  • Incremental ML Pipeline - Intelligent model updates based on data changes
  • Enterprise Security - Keycloak SSO, Kong API Gateway, RBAC
  • AI Analytics Chatbot - Natural language queries with 92% accuracy, intelligent 4-layer routing with GPT-4o

4. Incremental ML Pipeline

🔬 Research Background

This implementation draws from cutting-edge database research: Incremental View Maintenance (IVM), Cost-Based Query Optimization, Learned Indexes, and Adaptive Query Processing.

4.1 Pipeline Flow

┌──────────┐ ┌──────────────┐ ┌──────────────┐ ┌──────────┐ │ FILE │───►│ CHANGE │───►│ LEARNED │───►│ COST │ │ UPLOAD │ │ DETECTION │ │ ROUTER │ │ OPTIMIZER│ └──────────┘ └──────────────┘ └──────────────┘ └──────────┘ │ │ │ │ │ Detects: Predicts: Optimizes: │ • Row changes • Strategy • Time │ • Schema drift • Confidence • Memory │ • Distribution • Reasoning • Cost │ │ │ │ ▼ │ │ ┌──────────────────┐ │ │ │ EXECUTE STRATEGY│◄─────────┘ │ └──────────────────┘ │ │ │ ┌───────────────────────────┼────────────────────────┐ │ ▼ ▼ ▼ │ ┌─────────┐ ┌─────────────┐ ┌─────────────┐ │ │ SKIP │ │ INCREMENTAL │ │ FULL │ │ │ (0s) │ │ (5s) │ │ RETRAIN │ │ └─────────┘ └─────────────┘ │ (120s) │ │ └─────────────┘ │ │ └─────────────────────────────────────┘ │ ▼ ┌──────────────────┐ │ FEEDBACK LOOP │ │ • Record Actual │ │ • Retrain Router│ │ • Calibrate Cost│ └──────────────────┘

4.2 Processing Strategies

Strategy Trigger Condition Action Cost
SKIP < 1% change, no drift Validate only, no update ~0 seconds
INCREMENTAL 1-15% change, low drift partial_fit() on delta ~1-5 seconds
PARTIAL_RETRAIN 15-40% change, moderate drift Retrain on affected subset ~10-30 seconds
FULL_RETRAIN > 40% change, schema change Complete model retraining ~30-120 seconds

11.1 Hybrid 4-Layer Routing Architecture

The chatbot uses a novel 4-layer routing system that optimizes for both speed and accuracy:

┌─────────────────────────────────────────────────────────────────────────────┐ │ USER QUERY │ │ "How many users have uploaded files?" │ └─────────────────────────────────────────────────────────────────────────────┘ │ ▼ ┌─────────────────────────────────────────────────────────────────────────────┐ │ LAYER 0: SAFETY FILTER ~0ms │ │ ├── Blocks: "delete all files", "drop table", "hack the system" │ │ └── Response: Polite refusal with guidance │ └─────────────────────────────────────────────────────────────────────────────┘ │ PASS ▼ ┌─────────────────────────────────────────────────────────────────────────────┐ │ LAYER 1: TEMPLATE SQL (Pattern Matching) ~30ms │ │ ├── Patterns: "how many users", "total storage", "file count" │ │ ├── Direct SQL: SELECT COUNT(*) FROM users │ │ └── 90% of queries handled here │ └─────────────────────────────────────────────────────────────────────────────┘ │ NO MATCH ▼ ┌─────────────────────────────────────────────────────────────────────────────┐ │ LAYER 2: EMBEDDING CLASSIFIER (Semantic Similarity) ~80ms │ │ ├── Model: all-MiniLM-L6-v2 (sentence-transformers) │ │ ├── 50+ training phrases per intent │ │ ├── Handles: "folks in the platform", "gimme user count yo" │ │ └── Threshold: 0.35 confidence │ └─────────────────────────────────────────────────────────────────────────────┘ │ NO MATCH or COMPLEX ▼ ┌─────────────────────────────────────────────────────────────────────────────┐ │ LAYER 3: TEXT-TO-SQL LLM (Dynamic SQL Generation) ~4-5s │ │ ├── Model: Ollama gemma2:2b (local, no API costs) │ │ ├── Handles: "users who uploaded more than 5 files" │ │ │ "files by Super Admin between Dec-Jan" │ │ │ "average file size per organization" │ │ └── RBAC-aware query generation with access control │ └─────────────────────────────────────────────────────────────────────────────┘

12.4 Cache Invalidation Strategy

The system uses automatic cache invalidation on data mutations:

  • Create: No invalidation needed (new data)
  • Update: Delete specific cache key immediately
  • Delete: Delete specific cache key + related list keys
# Example: Cache invalidation on user update
async def update_user(self, user_id: str, data: dict):
    result = await self.repo.update(user_id, data)
    await redis_client.delete(f"user:{user_id}")  # Invalidate
    return result
